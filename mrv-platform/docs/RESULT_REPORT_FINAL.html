1. 과제 개요와 한 줄 요약

과제실내 흰다리새우(RAS) 양식장용 통합관리 + 탄소 MRV(Measurement · Reporting · Verification) 플랫폼 고객 형태B2B 구독 웹앱 (START · PRO · ENTERPRISE 3단계 요금제) 핵심 가치단순 모니터링이 아니라 기준선 → 추천/제어 → 로그 → 전후비교 → MRV 증빙이 한 줄로 이어지는 시스템 범위사양서(00_개발의뢰서_MASTER 4장) 16화면 전부 + 기계실 현장 장비(라즈베리파이 키오스크) + 검증 체계
사양서 16화면의 기능 항목은 전부 들어갔고, 그 사슬이 제품 안에서 닫히는지를 실물 빌드에서 브라우저로 확인했다. 2026-11-06 에 main 에 병합되고 운영 사이트(www.shrimp365.kr/mrv)에 배포됐으며, 첫 조직과 owner 가 등록됐다. 로그인 없이 보는 공개 데모(/mrv/demo)도 만들었다. 사람이 DB 를 직접 만져야 끝나는 자리가 남아 있지 않다. 남은 것은 기능이 아니라 한계와 전제(12장)이며, 그 한계는 리포트가 스스로 인쇄한다.

이번 과제가 다른 모니터링 제품과 갈리는 지점은 "이 숫자를 믿어도 되는가" 에 답하도록 설계했다는 것이다. 산출 불가를 0 으로 바꾸지 않고, 배출계수 출처를 발행 시점에 얼리고, 잘못 넣은 기록을 지우지 않고 무효로 표시하고, 같은 입력이면 같은 출력이 나오는 것을 기계적으로 대조한다. 5장이 그 내용이다. 외부에 보여 줄 때도 같은 태도를 지켰다 — 공개 데모는 앱 화면을 익명에 여는 대신 시연 자료로 같은 컴포넌트를 그리고, 어떤 API 도 부르지 않는다(9장).

4. 화면별 구현 상세 (16화면)

사양서 4장의 순서를 따른다. 각 화면은 실제 빌드본에서 찍었다. 캡처는 화면의 윗부분을 보이고, 긴 화면은 핵심 구간을 잘라 실었다.

4-1. 로그인 · 멀티테넌시 START

Shrimp365 계정으로 로그인하면(ADR 0005·0006) 초대된 조직(Organization)에 들어간다. 역할은 Owner · Operator · Viewer 세 가지이고, 쓰기 창구마다 서버가 역할과 요금제를 검사한다. 초대되지 않은 계정은 안내 문구만 본다.

4-2. 사이트 개요 START

KPI 5종(전력집약도 EI · 폭기 EI · 사료요구율 FCR · 산소효율지수 OEI · 폐사율)을 카드로 보이고, 신호등(정상·주의·경고)은 색과 글자를 함께 쓴다. 산출 불가일 때는 0 이 아니라 어느 입력이 비어서 못 냈는지를 카드가 적는다. OEI 는 「잠정 지표」 배지를 달고 산식이 미확정이라는 사실을 값 옆에서 말한다. 온보딩이 덜 끝났으면 상단 띠가 다음 할 일을 가리킨다.

4-3. 통합 대시보드 START

전력 · 용존산소 · 수온 · pH · ORP · EC 시계열을 일별/시간별로 집계해 그리고, 수조별 비교를 켤 수 있다. 계측기가 없는 지표는 체크박스가 비활성이고 「계측기 없음」이라고 적는다. 범례는 계측기 id 를 그대로 보여 어느 계량기인지 현장에서 대조할 수 있게 했다.

4-4. 급이 · 폐사 · 전력 · 생산량 입력 START

KPI 의 분자와 분모를 모두 제품 안에서 받는다. 입식 등록(폐사율 분모) · 급이 · 폐사 · 전력(구간 사용량, 자료유형 필수) · 생산량(EI·FCR 분모, 산정 근거 필수)의 수기 폼과, 같은 다섯 가지의 기록지 CSV 업로드(견본 서식 내려받기 포함)가 있다. 잘못 넣은 생산량은 삭제가 아니라 무효 처리한다(5-3).

4-5. 알림 센터 START

DO 저하(critical) · 폐사 급증(warning) · KPI 위험(red) 세 종류를 일일 배치가 평가해 만든다. 구독은 사이트별 체크박스이고, 확인 처리하면 누가 언제 확인했는지가 남는다. OEI 는 미확정 지표라 기본 감시 목록에서 뺐다(5-9). 아래 캡처는 DO 2.4 mg/L 수기값과 폐사 2,400마리를 넣고 배치를 돌린 결과다.

4-6. 리포트 — 주간/월간 자동 생성 · PDF · 이메일 START

리포트는 사람이 생성 화면에서 만들거나, 설정의 「리포트 자동 생성 · 이메일 발송」 일정이 매일 00:30(UTC) 배치에서 만든다. 자동 생성은 같은 기간을 두 번 만들지 않고(last_period_end 에서 이어짐), 수신자마다 발송 기록 한 줄을 남긴다. 인쇄용 문서는 브라우저 인쇄로 PDF 가 된다.

4-7. 추천(운전 레시피) 보드 PRO

급이 · 산소 · 순환 세 추천값과 근거 문장을 보인다. 추천은 설비에 자동 적용되지 않는다. 같은 입력이면 같은 추천이 나오므로 값이 바뀔 때만 레시피 버전이 늘고, 운영자는 「다른 값으로 버전 남기기」로 자기 판단을 사유와 함께 기록할 수 있다.

4-8. SOP 라이브러리 PRO

정상 운영 일일 점검 · 수질 악화 · DO 저하 · 폐사 급증 네 시나리오의 표준 절차와 체크리스트. 체크리스트 실행 기록은 수조와 항목별로 남는다.

4-9. 전·후 비교 + 비교실험(A/B) PRO

잠긴 기준선(Before)과 지정 기간(After)을 같은 산식 버전으로 대조한다. 개선율은 지표 방향을 보정한 값이라 양수면 나아진 것이다. 같은 화면 아래에 비교실험이 있다 — 대조군·처리군 두 구간을 실험이 직접 들고 있고 결과는 조회 때마다 라이브로 산출되며 기준선 비교와 같은 표로 그린다. 구간은 겹칠 수 없고 결론에는 사유가 필수다.

4-10. MRV 리포트 — Scope 2 location · market-based 병기 PRO

리포트는 감축량 · Before/After 표 · 산식 전문(대입값 포함) · Scope 2 market-based · 근거 참조(기준선 ID · 스냅샷 ID · 배출계수 version · 출처) 순서다. 배출계수와 출처는 발행 시점에 얼려 저장되므로 계수 표가 나중에 바뀌어도 옛 리포트는 그대로다. 계약 전력 증서가 있으면 market-based 가 location-based 옆에 인쇄되고, residual mix 미공표라는 한계를 리포트가 항상 적는다.

4-11. 승인형 제어 콘솔 ENTERPRISE

추천 레시피 버전을 수조에 제안하면 pending → approved → applied 로만 간다. 승인 없이 적용하면 서버가 409 를 낸다. 이 화면은 설비를 직접 제어하지 않는다 — 승인된 값을 운영자가 현장에서 반영한 뒤 그 사실과 결과를 기록한다. 모든 전이는 감사 로그에 남는다.

4-12. 멀티사이트 관리 ENTERPRISE

조직의 모든 사이트를 같은 기간·같은 산식으로 벤치마크한다. 최고/최저 배지는 지표 방향을 보정한 것이고, OEI 열은 사업장마다 DO 목표대역이 다르므로 같은 척도가 아니라는 사실을 표 아래에 적는다. 두 번째 사이트부터 ENTERPRISE 를 요구한다.

4-13. 맞춤 리포트 빌더 ENTERPRISE

절(섹션) · 지표 · 표지 문구만 정하는 서식이다. 요약과 산식 전문은 뺄 수 없고, 리포트가 실제로 들고 있는 지표만 고를 수 있다. 서식은 발행 시점에 리포트 안에 얼려 들어간다.

4-14. 감사 로그 뷰어 ENTERPRISE

모든 제어·설정 변경이 대상(entity) · 동작(action) · 행위자 · before/after diff 로 남는다. 기준선 잠금, 무효 처리, 증서·서식·일정 생성, 제어 액션 전이가 전부 여기에 있다.

4-15. 설정 공통

사이트 등록(Owner) · 수조와 DO 목표대역(OEI 의 유일한 산출 조건) · 계측기 · 현장 장비 페어링 · 전력 배출계수(append-only, 출처 필수) · 계약 전력 증서 · 리포트 서식 · 자동 생성 일정 · KPI 산식 설정(쓰기 경계 검증)이 한 화면에 있다. 사이트 · 수조 · 계측기 등록이 제품 안에 들어오면서 새 고객을 SQL 없이 받을 수 있게 됐다.

4-16. 온보딩 마법사 공통

설치키트(수집 API 키) → 센서 매핑(계측기 등록) → 기준선 수집·잠금 → 유료 전환의 4단계. 각 단계의 완료 조건을 서버가 실제 데이터로 판정하므로 "완료" 표시가 거짓이 될 수 없다.

5. 증빙으로서의 정직성 — 집중한 14가지

심사·검증 대응에서 차별점이 되는 부분이다. 기능 목록이 아니라 "이 숫자를 믿어도 되는가" 에 답하는 설계다.

5-1. 산출 불가는 0 이 아니라 null 로 남기고, 왜인지 말한다

지표를 못 내면 0 으로 치환하지 않는다. 0 은 "아주 좋음" 으로 읽혀 거짓 증빙이 된다. 대신 지표마다 다른 사유와 할 일을 화면이 적는다 — 어느 입력이 비었는지, 어느 화면에 가서 무엇을 넣으면 채워지는지까지. 리포트에도 「산출 불가 사유」 절이 있다.

5-2. 지표를 켜는 입력을 전부 제품 안으로 들였다

증빙 플랫폼인데 핵심 분모·조건을 사람이 SQL 로 넣어야 하는 자리가 네 곳 있었다. 전부 메웠고, 새 SQL 없이 동작한다.

값무엇이 걸려 있었나넣는 곳
생산량(생체량)EI · 폭기 EI · FCR · OEI 네 지표의 분모입력 화면 (그림 4-4b)
DO 목표대역OEI 의 유일한 산출 조건설정 화면 (그림 4-15a)
입식 수폐사율의 분모입력 화면 (그림 4-4a)
사이트신규 고객 자체설정 화면 (그림 4-15a)

5-3. 잘못 넣은 생산량은 지우지 않고 무효로 표시한다 11/05

삭제하면 이미 발행된 리포트가 참조한 근거가 흔적 없이 사라진다. 그래서 행은 남기고 KPI 산입에서만 빼며, 누가 언제 왜 뺐는지가 감사 로그에 남는다. 되돌릴 수 있다. 사유는 필수다. 무효 처리된 줄은 화면에서 감추지 않는다(그림 4-4c·d).

5-4. 생산량의 산정 근거를 함께 받는다

실측 출하·계측량인지, 입식수 × 평균체중으로 계산한 값인지, 어림인지를 필수로 적게 한다. 계산·어림이면 무엇으로 계산했는지 근거 메모를 요구한다. 생존율 보정 여부도 3상태로 받는다 — 미기재와 미적용은 다른 사실이다. 리포트가 EI 분모를 만든 두 점의 근거를 인쇄하고, 실측이 아니면 경고한다.

5-5. 전력이 실측인지 계산값인지 구분해 저장한다

계량기 실측 / 계산 / 어림을 건별로 저장하고 리포트가 밝힌다. 사람이 넣는 창구에서는 필수다. 현장 장비는 자기 자료유형을 스스로 선언하고(그림 6-3), 이 칸을 모르는 구형 장비를 위해 수집 창구만 미기재를 허용한다.

5-6. 배출계수는 하드코딩하지 않고, 출처를 얼려서 인쇄한다

  • 2023년도 국가 전력배출계수 0.4173 tCO2eq/MWh (CO2e 기준 · 단년도 평균)
  • 출처: GIR 「2025년 승인 국가 온실가스 배출·흡수계수」 (2025-12-17 확정 · 2025-12-18 공표), 한국에너지공단 계수표 및 공표 보도자료로 교차 확인
  • emission_factors 테이블에 append-only 로 관리. 기존 행을 고치면 과거 리포트의 근거가 사후에 바뀌므로 '수정' 이 아니라 '새 version 추가' 만 둔다(그림 4-15b)
  • 리포트는 발행 시점의 계수와 출처를 얼려서 들고 있다. 출처가 빈 version 에는 「검증 대응 미비」 표시
  • CO2 단독 계수(0.4149)는 일부러 넣지 않았다 — 자동 선택이 gas_scope 를 보지 않아 CO2 단독값을 CO2e 로 집어 쓸 수 있다

5-7. Scope 2 는 location-based 와 market-based 를 나란히 보고한다 11/05

GHG Protocol Scope 2 Guidance 는 둘 중 하나를 고르라고 하지 않고 둘 다 보고(dual reporting)하라고 한다. REC·PPA·녹색프리미엄 증서를 등록하면 리포트 기간과 겹치는 만큼 시간 비례로 적용되어 market-based 가 location-based 옆에 인쇄된다(그림 4-10b). 증서는 배출계수가 낮은 순으로 적용해 입력 순서와 무관하게 같은 결과가 나온다.

한국에는 공표된 residual mix 가 없다. 정석은 계약 전력을 뺀 잔여 전력에 residual mix 를 쓰는 것인데 그 값이 없다. 그래서 잔여분에 계통 계수를 그대로 쓰고 그 대체를 리포트가 항상 명시한다 — 과소 산정일 수 있다는 사실을 적지 않는 것이 가장 나쁘다. 계통 평균보다 높은 계약 계수는 등록 단계에서 거절한다.

이 계층은 차분검증된 산식 모듈 바깥에 있다. market-based 는 산식이 아니라 배분 규칙이고, Scope 2 산식은 다시 쓰지 않는다(절대규칙 1 — 산식 중복 금지).

5-8. 기준선은 잠그기 전에 입력 충분성을 판정한다

잠긴 기준선은 불변이고(DB 트리거가 UPDATE/DELETE 거부, ADR 0002) 이후 모든 전·후 비교와 Scope 2 감축량의 원점이 된다. 원본은 기간 유효성만 보고 잠갔다 — 계측값 세 건으로 계산된 기준선도 영구히 박혔다. 되돌릴 수 없는 결정에 입력 가드(127 항목 검증)를 세웠다. 강행 경로는 남기되 사유 문자열을 요구하고 판정 결과 전체를 감사 로그에 남긴다.

5-9. OEI 는 「잠정 지표」로 표시하고, 기본 알림에서 뺐다 11/05

산소효율지수는 사업계획서에 산식이 없는 제안값이고(ADR 0003), 스케일 계수와 신호등 임계값은 실증 전 가정이다. 그 사실을 값 옆에서 말한다(그림 4-2 · 4-9a · 4-12). 아무 설정도 하지 않은 조직에서 미확정 지표로 빨간 알림이 나가지 않도록 기본 감시 목록에서 뺐다. 원본 Python 과 함께 고쳐 차분검증을 유지했다(알림 128 → 104건).

5-10. 맞춤 리포트 서식은 보여 주기만 바꾼다 11/05

절·지표·표지만 정한다. 산식·배출계수·기간은 서식이 건드리지 못한다 — 서식으로 숫자가 달라질 수 있으면 "어느 서식으로 뽑았느냐" 가 감축량을 바꾸는 변수가 된다. 요약과 산식 전문은 뺄 수 없다. 발행 시점의 서식이 리포트에 얼려 들어가므로 서식을 나중에 고쳐도 옛 리포트는 그대로다. 화면과 인쇄물이 같은 판정 함수를 쓴다.

5-11. 리포트 자동 생성은 같은 기간을 두 번 만들지 않는다 11/05

주간(직전 월~일)·월간(직전 달) 일정이 마지막 기간 끝에서 이어지므로 cron 이 하루 한 번 두드려도 월요일/1일에만 새 기간이 생긴다. 같은 기간에 리포트가 둘이면 어느 쪽이 근거인지 사람이 고르게 된다. 잠긴 기준선이 없는 사이트는 실패가 아니라 "아직 조건이 안 됨" 으로 적는다. 보냈다는 사실이 증빙이다 — 수신자마다 발송 기록 한 줄(성공·실패·보내지 않음).

5-12. 비교실험(A/B)은 "무엇을 바꿔 보았는가" 를 기록으로 남긴다 11/05

대조군·처리군 두 구간을 실험이 직접 들고 있고, 결과는 조회 때마다 라이브로 산출한다(발행물이 아니다). 기준선 비교와 같은 표로 그린다(그림 4-9b). 두 구간은 겹칠 수 없고 결론은 사유가 필수다.

5-13. 쓰기 경계에서 오염을 막는다

included_quality_flags 를 빈 목록으로 두면 EI 가 0 이 되어 「감축률 100%」가 나온다. 적산 원값이 EI 분자로 새는 길도 있었다. 쓰기 경계에서 422 로 거부하고, 목록을 넓히면 경고한다(58 항목 검증).

5-14. 멀티테넌시 · 감사 · 접근성

모든 쿼리 org 스코프, RLS 정책으로 조직 격리(새 표 5개도 같은 정책, ADR 0007). 모든 제어·설정 변경은 audit_logs 에 before/after diff 로 남는다(그림 4-14). 신호등은 색만으로 전달하지 않고, 본문 대비 AA 4.5:1 을 CSS 토큰에서 직접 계산해 검사한다(88쌍).

6. 현장 장비 (라즈베리파이 키오스크)

기계실 계량기 옆에 두는 7인치 터치스크린(800×480) 장비다. 수질 센서를 읽어 올리고, MRV 모드에서는 전력 지침 입력 단말이 된다. 아래 화면은 실제 장비 화면 코드(webui.py)를 그대로 띄운 미리보기(raspberry-pi/make-preview.py)에서 찍었다.

  • 운전 모드 3종을 1급 개념으로 분리: 양식장 · 스마트팜 · 탄소 MRV. 모드는 무엇을 먼저 보여 줄지를 가르고, 수질 수집·전송은 모드와 무관하게 계속된다
  • 4개 국어(한국어 · 영어 · 베트남어 · 인도네시아어) — 현장 인력 구성을 반영
  • 회선이 끊기면 보관했다가 복구 시 전송. 서버가 거부한 보관분은 삭제하지 않고 사유와 함께 남긴다(11장 결함 8)
  • 적산 지침 2건 규칙 — 장비가 직전 지침을 함께 보내 한 건만 넣어도 구간값이 나온다
  • 장비가 전력 자료유형(실측/계산)을 스스로 선언한다 — 계산값으로 설정된 단말은 그 사실을 화면에 적는다
  • 6자리 코드 페어링으로 수집 키 발급 — 원문 키는 장비가 한 번만 가져가고 DB 에는 해시만. 끊는 화면도 있다
  • 계측기가 많은 현장: 키오스크에는 매일 읽는 1~3대만 고르고, 나머지는 월 단위 웹 CSV
  • 장비 시계가 틀리면 지침 시각이 틀리므로 전송을 막고 화면에 알린다
  • 운영 병합(11/06) — main 1.10.0(환경·기상 · 무선 · 전력 회로 제어 · 관수)과 MRV 모드를 합치며 두 쪽의 운전 모드를 [webui] mode = shrimp | agriculture | mrv 로 통일했다. 옛 [device] mode 값도 별칭으로 읽는다. 운영 브랜치의 AMP 전용판(1.11.0)과 합친 최종 장비 버전은 1.11.1

8. 배포와 운영 반영

2026-11-06 에 작업 브랜치를 main 에 합치고(PR #48), 운영 브랜치에 main 을 다시 합쳐 운영 사이트에 올렸다.

8-1. main 병합 (PR #48)

  • 브랜치가 10월 1일 이후 main 과 갈라져 있어(main 118커밋 앞섬) 그대로는 45개 파일이 충돌했다. 마지막 동기화 지점을 기준으로 다시 3-way 병합해 실제 충돌을 12개 파일로 줄인 뒤 풀었다.
  • 웹 셸 6개 파일은 main 의 새 구조(관리자 콘솔 권한 판정, brand 토큰, 모드별 메뉴 배열)를 그대로 두고 MRV 진입 항목만 얹었다. /mrv 는 미들웨어 보호 경로에 추가.
  • 라즈베리파이 6개 파일은 main 1.10.0 기능과 MRV 모드를 둘 다 유지했다(6장).
  • 병합 후 재검증 전부 통과(7-3). Vercel 미리보기 빌드 성공 후 머지.

8-2. 운영 반영

  • Vercel 의 Production 브랜치가 main 이 아니라 작업 브랜치 claude/shrimp-water-quality-monitoring-aZ4EY 로 설정되어 있어, main 머지만으로는 운영에 반영되지 않았다(Preview 환경으로만 배포됨).
  • 그 운영 브랜치에 main 을 병합했다. 충돌 2개(설치 모듈 목록, 장비 버전) 해결, AMP 전용판이 MRV 콜백을 받으면 시작 시 죽던 결함을 함께 수정(11장 #13). 장비 1.11.1.
  • Vercel Production 배포 완료(08:24 UTC). www.shrimp365.kr/mrv 가 404 에서 로그인 화면으로의 307 로 바뀌었다 — MRV 가 운영에 올라갔고 미들웨어가 비로그인 접근을 막고 있다는 뜻이다.
  • 첫 조직(컬리버 · ENTERPRISE)과 owner 초대 행을 SQL 로 등록했다. 이 이메일로 처음 /mrv 에 들어오는 순간 서버가 로그인 계정과 연결하고 감사 로그에 남긴다.
구조상 한계. 운영이 main 이 아닌 작업 브랜치에서 배포되는 구조가 그대로다. 앞으로도 main 머지마다 운영 브랜치 병합이 한 번 더 필요하다. Vercel 프로젝트 설정의 Production Branch 를 main 으로 바꾸면 없어진다(13장).

9. 공개 데모 — 로그인 없이 보는 시연

외부에 플랫폼을 보여 줄 때 "로그인 없이 열어 달라" 는 요청이 있었다. 앱 화면을 익명에 열면 조직 격리와 감사 로그의 행위자가 사라지므로, 대신 저장소에 든 시연 자료만으로 같은 화면을 그리는 읽기 전용 페이지를 만들었다(/mrv/demo).

  • 숫자는 진짜 엔진 출력이다. 로컬 Supabase 스텁(무안 양식장 · 수조 2 · 계측기 3 · 30일) 위에 프로덕션 빌드를 띄워 실제 API 응답(KPI · 계측값 · 기준선 비교 · 서식+market-based 리포트 · 실험 · 알림 · 추천 · 제어 액션)을 그대로 담았다. 화면은 재계산하지 않는다.
  • API 를 한 번도 부르지 않는다. 익명 요청이 조직 자료에 닿는 길을 열지 않기 위해서다. 미들웨어는 /mrv/demo 하나만 보호에서 뺀다.
  • 앱 화면과 같은 컴포넌트(KPI 카드 · 시계열 차트 · 비교 뷰모델)로 그린다. 다른 그림을 그리면 데모가 실제보다 좋아 보일 수 있다.
  • 화면 위에 "시연 자료이며 실제 고객 자료가 아니다" 를 적고, 실제 플랫폼은 조직 초대제라는 사실과 로그인 길을 둔다. 초대되지 않은 계정의 안내 화면에서도 데모로 갈 수 있다.
  • 구조: /mrv 레이아웃을 뿌리(메타데이터)와 (app)/(세션 + 셸)로 나누고 앱 화면 13개를 route group 으로 옮겼다. 주소는 그대로다.

공개 데모는 2026-11-06 에 8장과 같은 경로(main 병합 → 운영 브랜치 병합)로 운영에 반영됐다 — www.shrimp365.kr/mrv/demo 에서 로그인 없이 열린다.

항목내용인쇄
market-based 의 residual mix 대체한국에 공표값이 없어 잔여 전력에 계통 계수를 쓴다. 값 자체는 과소 산정일 수 있다. 공표되면 계수 하나만 바꾸면 된다.✓

증서의 월별 배분연 단위 증서를 월 리포트에 시간 비례로 자른다. 월별 배분표가 있는 계약이면 실제와 다를 수 있다.✓

메일 공급자 미선정기본이 log(안 보냄)다. 업체를 정해 키를 넣기 전까지 메일은 나가지 않는다 — 그 사실은 발송 기록에 남는다.기록

13. 사람이 해야 하는 나머지

  • Vercel 환경변수 — CRON_SECRET(없으면 알림 배치와 리포트 자동 생성이 돌지 않는다) · MRV_MAIL_PROVIDER · MRV_MAIL_FROM · RESEND_API_KEY · NEXT_PUBLIC_SITE_URL
  • Vercel Production Branch 를 main 으로 변경 — 운영 브랜치 수동 병합을 없앤다
  • 현장 장비 1.11.1 꾸러미 서명·배포 — 장비 쪽 MRV 모드는 이 배포 뒤에 올라간다
  • 배출계수 1차 대조 — 0.4173 의 원문 PDF 쪽수까지 확정하려면 한 번 더 대조
  • 외부 대시보드 0.4663 과의 값 불일치 정리 — 이 플랫폼 안에는 그 값이 없다. 함께 제출할 때 어느 쪽을 쓸지 정해야 한다(섞으면 같은 기간에 두 배출량이 나온다)
  • owner 로그인 후 온보딩 4단계 완주 — 사이트 · 수조 · 계측기 등록은 설정 화면에서, 수집 API 키 발급은 운영진 게이트웨이를 거친다
  • SNS·외부 제출물 업로드 — 저장소가 하지 않는다
