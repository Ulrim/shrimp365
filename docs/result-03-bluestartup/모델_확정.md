# 보고 대상 계수 모델 확정

**결정** 2026. 10. 21. — 결과보고서에 보고할 계수 모델을 **현재 배포본으로 확정**한다.
**결정 사유** 저장소·현장 장비·배포 꾸러미에 실제로 들어 있는 유일한 모델이며,
학습 조건·평가 수치·내보내기 과정이 문서로 남아 있는 유일한 모델이다.

이 지문(sha256)이 **보고 기준점**이다. 모델을 바꾸면 이 문서와 결과보고서의 수치가
동시에 무효가 되므로, 바꿀 때는 이 문서를 먼저 고친다.

### 확정된 모델인지 확인하는 법

```
vision/.venv/bin/python docs/result-03-bluestartup/src/model-spec.py
```

출력 머리에 `확정 모델과 일치` 가 찍히면 배포본이 이 문서가 가리키는 그 파일이다.
`⚠ 불일치` 가 찍히면 누군가 모델을 교체한 것이고, **그 상태의 수치는 보고에 쓸 수 없다.**

## 2. 폐기하는 선택지 — 0.7642 모델

과거 보고에 등장한 mAP 0.7642 모델(라벨 300장·1,017개체)은 **저장소 어디에도 없다.**
전 브랜치를 검색해도 가중치 파일도, 그 수치를 만든 코드·로그도 나오지 않는다
(개발진척점검 2026-10-10 확인).

그 모델로 보고하려면 가중치 원본을 외부에서 확보해 저장소에 넣고, 평가를 다시 돌려
출력을 남겨야 한다. **확보 여부가 불확실한 자산에 보고를 걸 수 없으므로 폐기한다.**
두 모델을 섞어 쓰는 선택지는 애초에 성립하지 않는다 — 수치와 산출물이 어긋난다.

## 3. 문서 수치와 배포 파일이 같은 것인가 — 대조 결과

`docs/VISION_MODEL_TRAINING.md` §8 「실제 학습 결과 (2026-10-02)」가 이 모델의 근거다.
문서가 말하는 산출물과 저장소 파일이 같은 것인지 대조할 수 있는 속성을 전부 맞춰 봤다.

| 속성 | 문서 §8 | 저장소 파일 | 대조 |
|---|---|---|---|
| 해상도 | 416 | 입력 1×3×**416**×416 | 일치 |
| 용량 | 12.2MB | 12,168,743바이트 (12.17MB) | 일치 |
| 클래스 수 | 새우 1종 | 1 | 일치 |
| 시점 | 2026-10-02 학습 | 2026-10-02 커밋 | 일치 |

**확인 가능한 네 속성이 모두 맞는다.** 다만 아래 4장의 한계가 남는다.

## 4. ⚠ 보고서에 쓸 때 반드시 지킬 것 — 수치의 조건을 섞지 말 것

문서 §8 에는 오차율이 **두 가지 조건**으로 적혀 있고, 둘은 서로 다른 것을 잰 값이다.
이것을 섞으면 점검에서 바로 문제가 된다.

| 수치 | 무엇을 쟀나 | 어떤 산출물로 쟀나 |
|---|---|---|
| **계수 오차 2.2%**, ±20% 안 98.9% | **test 445장** (학습·검증에 한 번도 안 쓴 데이터) | `.pt`, 640px, conf 0.35 |
| **계수 오차 5.0%**, ±20% 안 91.3%, 34ms | **밀집 valid 185장** (11마리 이상만 추린 어려운 부분집합) | **416 ONNX — 확정된 배포본** |

즉 **“배포 모델의 계수 오차는 2.2%”라고 쓰면 조건을 섞는 것이다.**
2.2% 는 같은 학습에서 나온 `.pt`(640px)를 test 전체로 잰 값이고,
배포본인 416 ONNX 를 test 전체로 잰 값은 문서에 없다.

### 권장 표기 — 둘 중 하나

**(A) 확보된 자료만으로 쓰는 경우 (지금 바로 가능)**

> 배포 모델(416 ONNX)은 밀집 장면(11마리 이상) 185장 기준 계수 오차율 5.0%,
> ±20% 이내 91.3%, 처리시간 34ms(x86 CPU 4코어)이다. 동일 학습의 PyTorch 가중치를
> 미사용 데이터 445장으로 평가한 결과는 평균 오차율 2.2%, ±20% 이내 98.9% 이며,
> 두 산출물은 동일 부분집합에서 5.0% 대 5.3% 로 사실상 동등하다.

마지막 문장이 중요하다 — 문서 §8 이 **같은 185장에서 ONNX 5.0% 와 `.pt` 5.3%** 를
나란히 재 두었으므로, "내보내기로 성능이 깎이지 않았다"는 주장은 근거가 있다.
다만 *"그러므로 416 ONNX 도 test 445장에서 2.2% 일 것"* 은 **추정이지 측정이 아니다.**
추정을 측정처럼 쓰지 말 것.

**(B) 가장 깔끔한 방법 (평가 데이터셋 확보 후)**

416 ONNX 로 **test 445장**을 다시 평가해 한 줄로 보고한다. 그러면 조건이 하나가 되고,
아래 5장의 한계도 함께 해소된다.

```
vision/.venv/bin/python vision/ai/trainer/eval_count.py \
  --model vision/ai/models/shrimp_yolov8n_416.onnx --split test
```

(실행 후 **출력 JSON·CSV 를 `docs/result-03-bluestartup/evidence/` 에 커밋**할 것.)

## 5. 남은 한계 — 모델을 확정해도 해소되지 않는 것

모델 확정은 "어느 파일로 보고할지"를 정한 것이지, "그 수치를 검증했다"는 뜻이 아니다.

- **학습·평가 데이터셋이 저장소에 없다.** 따라서 mAP 0.924, 오차 2.2%·5.0% 를
  **재계산해 확인할 수 없다.** 지금 이 수치들의 근거는 `VISION_MODEL_TRAINING.md` §8
  서술 한 곳뿐이고, 그것을 뒷받침할 학습 로그·평가 JSON·결과 CSV 는 커밋되어 있지 않다.
- 해소 방법은 하나뿐이다 — **데이터셋을 확보해 평가를 재실행하고 출력 파일을 커밋**한다.
  그 전까지 결과보고서의 성능 수치는 "문서 기재값"이지 "재현 가능한 측정값"이 아니다.
- **현장 데이터로 잰 값이 아니다.** 위 수치는 모두 학습에 쓴 데이터셋(shrimp_cf +
  Counting PL)의 분할에서 나온 것이다. 실제 수조에서의 정확도는 카메라를 현장에
  고정한 뒤에야 잴 수 있다.
