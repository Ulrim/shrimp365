## 0. 결론 먼저

**"개발된 것이 없다"가 아니다. 전제를 정정한다.**

| 구분 | 상태 |
|---|---|
| 웹 플랫폼 (클라우드 서버 + 애플리케이션 계층) | **상당 수준 구현** — 화면 29개, Supabase 마이그레이션 85개, 생산관리·수익분석 탭 가동 |
| 엣지 장비 (센서 노드 계층) | **상당 수준 구현** — `raspberry-pi/` 24개 파일, 수집·판정·권고·경보·OTA·버퍼링까지 현장 동작 |
| 비전 기반 급이 최적화 | **전무** — 코드 0줄, 사업비 4,500천원이 배정된 항목 |
| 수익성 **예측** 엔진 (성장곡선·예상이익·출하윈도우) | **미구현** — 현재 지표는 전부 수확 완료 후 사후 집계. 실제로는 **엔진 5종 + 출력 계층 1종**을 만들어야 한다(4절) |
| 통신 아키텍처 (MQTT·게이트웨이 계층·시계열 파티셔닝) | **미구현** — 계획서 4계층 중 2계층이 독립 컴포넌트로 존재하지 않음 |
| 다국어 리포트 엔진 | **미구현** — UI 번역 사전(ko/en/vi/id)은 있으나 리포트 생성 엔진 없음, **태국어 미지원** |

한 줄로 줄이면 — **"보여줄 화면과 현장 장비는 있고, 이 사업의 아이템명에 적힌 두 단어(`AI 기반 운영분석`의 예측 부분과 `출하의사결정`)가 아직 비어 있다."**

그리고 코드와 별개로 더 급한 문제가 있다. **계획서와 코드가 어긋난 지점 세 군데**(측정 주기, 암모니아 센서, 유료화 비활성)는 점검위원이 계획서를 펼쳐 놓고 대조하면 즉시 드러난다. 8절에 따로 뺐다. 이 중 **측정 주기는 2026. 10. 01. 사용자 결정으로 서류 정정으로 종결**되어 코드 작업이 사라졌다.

즉, 7단계 실증을 그대로 끌면 **실증할 기능이 절반 비어 있는 상태로 실증에 들어간다.** 4개월을 실증에 다 쓸 수 없고, 앞 단계를 압축해 넣어야 한다. 아래 계획은 그 압축안이다.

## 4. 만들어야 하는 엔진 — 5종 + 출력 계층 1종

계획서가 "수익성 예측 엔진" 한 덩어리로 적은 것은 실제로는 **서로 입력을 주고받는 엔진 5종 + 출력 계층 1종**이다. 하나로 보면 착수 순서를 틀린다.

**의존 순서가 이 절의 핵심이다.**

```
엔진1 (성장곡선) ──→ 엔진2 (수익성 예측) ──→ 엔진3 (출하 윈도우)
   │
   ├──→ 엔진4 (리스크 조기경보)
   └──→ 엔진5 (급이 최적화)

엔진1~5 ──→ 엔진6 (다국어 리포트 출력 계층)
```

| 관계 | 내용 |
|---|---|
| 직렬 | `엔진1 → 엔진2 → 엔진3` |
| 분기 | `엔진4`·`엔진5`는 엔진1에서 갈라져 나온다 |
| 출력 계층 | `엔진6`은 엔진 1~5 전체의 출력을 받는다 |

**엔진 1이 나머지 전부의 전제다.** 엔진1 없이 2·3·4·5에 손대면 전부 가정값 위에 쌓게 되고, 나중에 엔진1이 들어오는 순간 다시 만들어야 한다. 착수 순서를 바꾸지 않는다.

| 엔진 | 이름 | 계획서 대응 | 6절 과업 |
|---|---|---|---|
| 1 | 생육 성장곡선 엔진 | 5단계 "AI 생육 성장곡선" | 2-1 |
| 2 | 수익성 예측 엔진 | 5단계 "예상 영업이익" | 2-2 |
| 3 | 출하 의사결정 엔진 | 아이템명 `출하의사결정 지원` | 2-3 |
| 4 | 생산·경제 리스크 조기경보 엔진 | 5단계 "리스크 조기경보" | 2-4 |
| 5 | 급이 최적화 / 사료 효율 엔진 | 3단계 "사료 효율 5~10% 개선" | 3-4 |
| 6 | 다국어 리포트 출력 계층 | 6단계 "동적 리소스 매핑 엔진" | 4-1 |

### 엔진 1. 생육 성장곡선 엔진 — 토대

| 항목 | 내용 |
|---|---|
| 하는 일 | 입식일부터 현재까지의 성장 곡선을 적합하고, 향후 ABW·생존율·바이오매스를 예측한다 |
| 입력 | `growth_samples`(abw_g·survival_rate·estimated_biomass_kg 시계열), `production_cycles`(stocking_date·stocking_count·initial_weight_g·pl_species·pl_stage), `water_quality_readings.temperature` |
| 출력 | 현재 추정 ABW·생존율·바이오매스, 향후 일자별 예측 곡선, 예측 구간(불확실성) |

**왜 토대인가.** 예상 매출도 출하 시점도 전부 "그때 새우가 몇 g이고 몇 마리 살아 있나"에서 나온다. 이것 없이는 엔진 2·3·4·5가 전부 성립하지 않는다.

**모델 방향(지훈이 확정).** 새우 성장은 강한 온도 의존성을 가지므로 **적산수온(degree-day)** 을 시간축으로 쓰는 것이 정석이다. 곡선형은 von Bertalanffy / Gompertz 등 후보를 비교해 확정한다.

**기술적 요점.** **샘플링은 드문드문(주 단위), 수온은 60초마다** 들어온다. 성긴 성장 관측과 조밀한 환경 시계열을 묶는 축이 적산수온이다. 달력 날짜를 시간축으로 쓰면 수조별·계절별 편차를 흡수하지 못한다.

### 엔진 2. 수익성 예측 엔진

| 항목 | 내용 |
|---|---|
| 하는 일 | 진행 중 사이클의 **예상** kg당 원가·예상 매출·예상 영업이익 산출. 현재 코드는 수확 후 사후 집계뿐이다 |
| 입력 | 엔진1 출력 + `cycle_costs`(누적 실적) + 잔여기간 추정비용(사료·전기·인건) + 시장 단가 |
| 출력 | 지금 출하 시 / N일 뒤 출하 시의 원가·매출·이익 시나리오 |

**기존 코드와의 관계.** `app/(dashboard)/production/page.tsx`의 `costPerKg`·`profit`·`roi` **위에 올린다. 다시 만들지 않는다.** 사후 집계 산식은 예측값의 검증 기준으로도 그대로 쓴다.

### 엔진 3. 출하 의사결정 엔진 — 아이템명의 핵심

| 항목 | 내용 |
|---|---|
| 하는 일 | 최적 출하 윈도우(날짜 구간)를 근거와 함께 제시. 현재는 `target_harvest_date` 수동 입력뿐이다 |
| 입력 | 엔진1(성장) + 엔진2(수익성) + 엔진4(리스크) + **크기별(마리수/kg) 시장 단가** |
| 출력 | 추천 구간 + 근거 수치 전량 노출(블랙박스 금지) |

**판단 구조.** 더 키우면 총중량이 늘고 **큰 새우일수록 kg당 단가가 오른다.** 그러나 사료비가 계속 들고 폐사 리스크가 누적된다. **한계수익 = 한계비용** 이 되는 지점이 출하 적기다.

> **치명적 전제: 크기별 시세 데이터가 없으면 이 엔진은 성립하지 않는다.** 5절 데이터셋 표 참조.

### 엔진 4. 생산·경제 리스크 조기경보 엔진

| 항목 | 내용 |
|---|---|
| 하는 일 | 현재 수질에만 있는 경보를 생산·경제 지표로 확장한다 |
| 경보 대상 | 성장 정체(엔진1 예측 대비 실측 ABW 하회), 생존율 급락, FCR 악화, 원가 초과(예상 원가가 목표 단가를 넘어섬) |
| 입력 | 엔진1 **잔차**(예측−실측), `journal_entries.mortality_count`, `diagnosis_results`, 기존 수질 이상탐지 |

**기존 코드와의 관계.** `raspberry-pi/anomaly.py`와 `lib/thresholds.ts`의 판정 구조를 **재사용**한다. 경보 전달은 기존 웹푸시를 탄다. 새 경보 체계를 만들지 않는다.

### 엔진 5. 급이 최적화 / 사료 효율 엔진 — 비전과 맞물림

| 항목 | 내용 |
|---|---|
| 하는 일 | 권장 급이량 산출, FCR 추이 추적, 과잉급이 경고 |
| 입력 | `journal_entries.feeding_amount`(일일 급이량 kg) + 엔진1 바이오매스 + 수온·DO + **비전 지표(활동량·사료반응성·개체크기)** |

**「사료 효율 5~10% 개선」 정량목표를 측정하는 주체가 이 엔진이다.**

비전 없이도 1차 버전(바이오매스 기반 급이율 표)은 가능하다. 비전은 2차에서 교차검증으로 붙인다.

> **주의.** 정량목표를 주장하려면 **개선 전/후 비교 설계**가 먼저 있어야 한다. 엔진보다 측정 설계가 앞선다. 지금처럼 FCR이 실계정에서 `null`인 상태로는 개선 전 기준선 자체가 없다(2절 13번).

### 엔진 6. 다국어 리포트 출력 계층

계획서가 "동적 리소스 매핑 엔진"이라 부른 것. 엔진 1~5의 출력을 **언어 비종속 DTO**로 만들고 View 단계에서 언어 리소스를 매핑한다.

**설계 제약이 앞 엔진들에 걸린다.** 엔진 1~5가 처음부터 **문장이 아니라 구조(코드+수치)를 반환하도록** 설계해야 이 계층이 성립한다. 나중에 문자열에서 구조를 역추출할 수는 없다.

`raspberry-pi/advice.py`가 이미 이 방식이다 — 파일 주석에 "문장은 여기서 만들지 않는다 — 화면이 4개 국어를 쓰므로 코드만 돌려주고 번역은 화면이 맡는다"라고 적혀 있고, 반환 단위는 `{"code", "level", "value", "digits"}` 구조다. **같은 원칙을 서버 엔진에도 적용한다.**

### 5-3. 외부 데이터 — 조사 필요

아래는 **후보이며 지훈이 실제 입수 가능성·갱신 주기·라이선스를 확인해야 한다. 확정 사실로 쓰지 말 것.**

| 후보 | 용도 | 확인할 것 |
|---|---|---|
| 흰다리새우 크기별 도매 시세(공판장·수협·도매시장 통계 계열) | 엔진 3의 치명 입력 | 사이즈 구간이 실제로 구분되어 공시되는가, 갱신 주기, 재배포 가능 여부 |
| 통계청 어업생산동향조사 / 해양수산부 국내 새우 시장현황 | 시장 규모·단가 추세 | **계획서 부록 01이 이미 인용한 출처**라 정합성이 좋다 |
| 흰다리새우 성장 모델 문헌값(곡선 계수·온도 의존 파라미터) | cold start | 양식 환경(수온·밀도)이 국내 조건과 비교 가능한가 |

### 5-4. 데이터 부족을 다루는 방법

완료 사이클이 적을 가능성이 높다. 2단 전략을 전제로 설계한다.

| 단계 | 내용 |
|---|---|
| 1. **Cold start** | 문헌 파라미터 + 적산수온으로 시작한다. 농가 데이터 0건에서도 곡선이 나온다 |
| 2. **농가별 보정** | 사이클이 쌓이면 해당 농가·수조의 실측으로 파라미터를 당긴다 |
| 3. **백테스트 규약** | 종료된 사이클에서 중간 시점까지만 입력하고 실제 수확 ABW·수확량과의 오차를 기록한다. **이 오차표가 성능 증빙이 된다** |

### 하지 말 것

- **이미 있는 것을 다시 만들지 말 것.** 엣지 이상탐지(`anomaly.py`), 운전 권고(`advice.py`), 버퍼링(`buffer.py`), 생산관리 테이블(`production_management.sql`), 사후 수익 집계(`production/page.tsx`), i18n 라우팅(`lib/i18n/`)은 구현되어 있다. 엔진 2는 `production/page.tsx`의 기존 `costPerKg`·`profit`·`roi` **위에 예측을 올리는 것**이고, 엔진 4는 `lib/thresholds.ts`의 판정 구조를 **재사용하는 것**이며, 엔진 6은 `lib/i18n/`을 **버리는 것이 아니라 리포트 경로를 그 위에 붙이는 것**이다.
- **엔진 1을 건너뛰고 2·3·4·5에 손대지 말 것.** 전부 가정값 위에 쌓게 되고, 엔진 1이 들어오는 순간 다시 만든다.
- **엔진이 완성된 문장을 반환하게 만들지 말 것.** 엔진 6이 성립하지 않는다. 구조(코드+수치)로 돌려주고 번역은 View가 맡는다.
- 라우팅·캐싱·서버 액션 설계를 기억으로 쓰지 말 것. 이 저장소는 **Next.js 16.2.4**다. 착수 전 `node_modules/next/dist/docs/`의 해당 가이드를 읽는다.

## 9. 사람이 해야 하는 일 — 에이전트가 못 한다

| # | 항목 | 비고 |
|---|---|---|
| 1 | **실증 양식장 섭외·현장 설치** | 7단계의 전제. 실증고객 2~3개소가 매출 목표의 근거다. `install.sh`·`setup-kiosk.sh`로 설치 자동화는 준비되어 있으나 물리적 설치는 사람 몫 |
| 2 | **부품 조달** — 라즈베리파이 10개, DO/pH/수온 센서 8식, **카메라 모듈+수중조명 5식**, PCB/기구·보호케이스 | 3차(비전) 착수의 선행 조건. 카메라·조명이 입고되지 않으면 3-2 이후가 멈춘다 |
| 3 | **홍보 동영상 1개 제작** | 협약기간 내 산출물. 저장소 밖 작업 |
| 4 | **협약 서류 수정·변경 보고** | 8절의 측정 주기·센서 구성·산출물 형태. **측정 주기는 "10분 주기 이상(60초 측정)" 정정 문구를 민준이 작성하고, 기관 제출은 사람이 한다** |
| 5 | **Supabase SQL 실행** | DB 쓰기에는 service_role 키가 필요하고 이 저장소에 그 키는 없다. 마이그레이션 커밋까지가 에이전트의 일이고 **실행은 사람이 SQL Editor에서 한다** |
| 6 | **가격 정책 확정** | 6절 1-2를 구현하기 전에 기본형/확장형 기능 경계와 금액을 사람이 결정해야 한다 |
| 7 | **실증 현장 사진·시험 기록 촬영** | 점검 증빙은 실제 촬영본만 쓴다 |
| 8 | **완료된 과거 사이클이 운영 DB에 몇 건 있는지 확인** | **엔진 1 적합의 학습 데이터다.** 저장소로는 알 수 없고 Supabase를 열어야 안다. 건수가 부족하면 5-4의 cold start 전략으로 간다. **2-1 착수 전에 알아야 한다** |
| 9 | **크기별(마리수/kg) 시세 출처 확보** | **엔진 3의 치명 전제.** 공공 통계로 갈지 농가 실입금 단가 입력으로 갈지 사람이 정한다. 유료 데이터면 계약·비용 판단이 필요하다. 지훈이 후보를 조사하되 **채택은 사람이 결정한다** |

## 10. 한 장 요약

| | 내용 |
|---|---|
| **현황** | 웹 플랫폼(화면 29개·마이그레이션 85개)과 엣지 장비(`raspberry-pi/` 24개 파일)는 상당 수준 구현. 7단계 중 1·2·4·5·6단계가 `◐`, 3·7단계가 `❌` |
| **핵심 공백** | 비전 모듈(사업비 4,500천원 배정, 코드 0줄) · 수익성 **예측** 엔진 · 다국어 리포트 엔진과 태국어 |
| **"수익성 예측 엔진"의 실체** | 하나가 아니다. **엔진 5종 + 출력 계층 1종.** `엔진1(성장곡선) → 엔진2(수익성) → 엔진3(출하윈도우)` 직렬, `엔진4(리스크)·엔진5(급이)`는 엔진1에서 분기, `엔진6`은 전 엔진의 출력 계층. **엔진 1이 나머지 전부의 전제다** |
| **데이터** | 엔진 1·2·4·5의 1차 버전 입력은 **이미 스키마에 있다.** 막는 것은 둘 — **크기별 시세 데이터 부재(엔진 3 불가)** 와 **완료 사이클 이력 부족 가능성(엔진 1 cold start 필요)** |
| **숨어 있던 선결 과제** | `total_feed_kg` 컬럼이 DB에 없어 **FCR이 실계정에서 항상 `null`**, `journal_entries`에 `cycle_id`가 없어 급이·폐사를 사이클에 못 붙인다. 계획서 항목은 아니나 엔진 2·5의 선결 조건이라 2-0에서 먼저 친다 |
| **가장 급한 서류 문제** | 남은 것은 **두 건** — 암모니아 센서, 유료화 비활성. 측정 주기(10분 vs 60초)는 **2026.10.01 결정으로 서류 정정 종결, 코드 변경 없음** |
| **권고 순서** | 서류 봉합·유료화(10월 1~2주) → **2-0 데이터 선결 → 엔진 1~4**(10월 3주~11월 2주) → 비전 최소 기능 + 엔진 5(11월) → 엔진 6 + 태국어(11월 말~12월) → 통신 아키텍처(12월) → 실증·산출물 정리(12월 말~27.01) |
| **미루는 것** | 전원모듈·LoRa/LTE, 비전 AI 고도화, 전력 kWh 기록. MQTT·게이트웨이는 설계 문서까지 |
| **사람이 먼저 답해야 할 것** | ① 완료 사이클이 DB에 몇 건인가 ② 크기별 시세를 어디서 받는가 ③ 기본형/확장형 가격 경계 — 셋 다 2차 묶음 착수를 좌우한다 |
